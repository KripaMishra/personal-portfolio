## Start with the boundary you can defend

Privacy tooling is often described in terms of eventual capability: better recall, more entity types, richer models, deeper auditing, reversible masking, document pipelines. The public `mastra-pii` Alpha 1 README argues for a more grounded starting point.

Its current scope is deliberately narrow: deterministic, local redaction for Mastra, built around `@openredaction/core/lite`, with no network or model calls during redaction. The README also says the package rejects `ner` and `model` layers, keeps detector internals private, and returns either redacted text or a generic `[REDACTION_FAILED]` marker when things go wrong.

That combination is the article's core lesson. If an agent pipeline handles sensitive text, the first public release does not need to solve every privacy problem. It does need a failure mode that is understandable and hard to misread.

## What Alpha 1 actually contains

The public README documents a compact but clear surface area:

- an asynchronous `redactText()` API
- a Mastra `Processor`-compatible `processor`
- deterministic placeholders such as `[EMAIL_1]`
- stable handling for a bounded entity set including email, phone, SSN, credit card, bank account, IP address, passport, address, name, date of birth, token, UUID, and medical ID
- optional custom regex patterns with entity labels and priorities
- deterministic merging of overlapping spans
- right-to-left placeholder application

Just as important, the README spells out what Alpha 1 is not. It does not implement Transformers.js NER, a Mastra `PIIDetector` model layer, reversible restoration, audit logs, telemetry, or structured document redaction. It also says invalid input and detector failures fail closed locally, while explicitly refusing to claim perfect PII recall.

That is unusually healthy public documentation. It gives future readers a reason to trust the project because it does not hide its edges.

## Why fail-closed behavior matters in agent systems

Agent stacks create many more places for sensitive text to leak than a normal request/response app. A message can appear in prompts, tool inputs, tool outputs, traces, logs, memory, analytics, background retries, or exported artifacts. Once that happens, "we meant to redact it later" stops being a convincing safety story.

The public `mastra-pii` README takes the opposite approach. It narrows the first release to a deterministic layer, keeps raw detector objects private, and makes failure visible by returning a generic marker instead of pretending the text was handled safely.

That design does not guarantee perfect coverage. The README says so directly. But it does reduce a more dangerous failure mode: silent confidence.

In other words, the system is allowed to be incomplete, but it is not allowed to look complete when it is not.

## Deterministic first is a product choice, not just an implementation shortcut

It is tempting to read "deterministic only" as a temporary engineering compromise. The better interpretation is that it is also a product-positioning choice.

Deterministic behavior gives a few practical benefits that matter in early agent infrastructure:

- behavior is easier to explain from public documentation
- placeholder output is stable across runs
- custom patterns let callers cover domain-specific identifiers without retraining anything
- callers can reason about what is and is not in scope
- failure handling can stay local instead of depending on remote services

That makes the package easier to integrate into sensitive pipelines where privacy boundaries matter more than maximal recall.

The tradeoff is equally important: the README keeps free-form name and address heuristics disabled by default and rejects broader `ner` and `model` layers. So the package is not selling a universal privacy shield. It is offering a disciplined baseline.

## The public limits are part of the value

A strong portfolio article should not erase the constraints. It should center them.

The README warns that regexes should be bounded and reviewed by callers, that no detector can guarantee every arbitrary identifier or name, and that the package is only prepared for `0.1.0-alpha.1` without claiming publication from that repository change. Those statements make the package feel more serious, not less.

The reason is simple: privacy work becomes risky when marketing language outruns operational truth.

This article draft should therefore make a clear distinction between two claims:

1. What the public package does today: deterministic local redaction with explicit guarantees and explicit exclusions.
2. What it intentionally does not claim: complete recall, model-backed coverage, or finished production governance.

That framing is especially useful in a portfolio because it demonstrates judgment, not just implementation.

## Where this article can go deeper than a project card

A project card can summarize the package in one sentence. An article can make the broader argument.

The broader argument is that privacy tooling for agents should start with a boundary that degrades safely. If the first release can only defend deterministic local redaction, then the public docs should say exactly that. Additional layers can come later, but they should be added as new trust assumptions, not smuggled in as implied capability.

That is the most interesting technical idea in the current public evidence, and it is strong enough to stand on its own as writing.

## What this article should not overclaim

This draft should not imply that `mastra-pii` already solves general document redaction, broad natural-language entity recognition, or production observability. It should not imply that the package is already published or widely adopted. It should not use real PII examples.

If examples are added later, they should stay synthetic and obviously synthetic.

## Why this belongs in the portfolio

The portfolio specification asks for evidence-backed writing tied to real technical decisions. This draft meets that bar because it extracts one durable lesson from the public README:

In privacy-sensitive agent systems, honest limits plus fail-closed behavior can be more valuable than broader-but-ambiguous capability.

That is a concrete engineering stance, not a placeholder theme.
